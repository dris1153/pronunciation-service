# 採点定数の根拠

ハードコードされた各採点定数が、なぜその値になっているのかを説明します。いずれかを変更する場合は、サニティスイートの実行が必要です。

```
python scripts/sanity_eval.py \
    --api-key=$API_KEY \
    --compare-baseline=tests/sanity_dataset/sanity_baseline.json
```

比較ツールが 5pt を超える乖離や、ティアの入れ替わりを報告した場合は、次のどちらかを判断します。

- **意図的な再キャリブレーションか?** → `sanity_baseline.json` を更新し、
  変更内容をここに記録する。
- **リグレッションか?** → 元に戻す。

---

## 1. GOP キャリブレーション: `_FLOOR = -25.0`、`_CEIL = -3.0`

- **場所:** `app/services/gop_service.py`（正規化のステップ）
- **経験則:** 正しく発音された音素の CTC 対数確率は、おおよそ -25（非常に悪い）から
  -3（非常に良い）の範囲に収まります。完璧な TTS であっても -3 を超えることはまれです。
  softmax の質量が語彙全体に分散されるためです。
- **変更した場合のリスク:** 線形の再マッピングなので、すべての GOP スコアが比例してずれ、
  accuracy_score（重み 45%）と overall_score に波及します。

## 2. 音素の類似度による部分点: `0.3`

- **場所:** `app/services/pronunciation_service.py` — 音素アライメントの
  コスト行列。
- **経験則:** 音素を同じ音声学的グループの音素に置換した場合（例: ɛ↔æ、どちらも前舌母音）、
  一致なら 1.0、異なるグループなら 0.0 のところ、0.3 が与えられます。これより高い値にすると、
  Azure のより厳しい採点に比べて正確さが水増しされ、低い値にすると、軽微なアクセントの違いを
  厳しく罰しすぎます。
- **変更した場合のリスク:** 音素ごとの正確さがずれる → 集計した IPA 正確さが
  線形に動く → accuracy_score（重み 55%）がずれます。

## 3. 誤発音のしきい値: `60.0`

- **場所:** `app/services/pronunciation_service.py` —
  `_MISPRONUNCIATION_THRESHOLD`。
- **根拠:** Azure Speech SDK の慣例に合わせています。IPA 正確さが 60% 未満の単語は
  誤発音としてフラグが立ちます。
- **変更した場合のリスク:** 単語レベルの `error_type` の分類がずれます。新たに
  誤発音と分類された単語は、`completeness_score` に算入されなくなります。

## 4. Wav2Vec2 のホップサイズ: `320`

- **場所:** `app/services/pronunciation_service.py` — `_HOP_SIZE`。
- **根拠:** Wav2Vec2 のアーキテクチャでは、16 kHz で 20 ms のフレーム = 1 フレームあたり 320 サンプルです。
  `fluency_score` に入力される、単語タイミングの強制アライメントに使われます。
- **変更した場合のリスク:** ホップが変わるモデルに差し替える場合は、この定数も必ず更新する必要があります。
  更新しないと単語タイミングが誤り → 流暢さの指標が無意味な値を返します。
- **CI ガード:** ホップを更新せずにモデルをアップグレードした場合、サニティスイートがずれを検出します。

## 5. 速度ペナルティの不整合: `30 pts/wps`（韻律）と `20 pts/wps`（流暢さ）

- **場所:** `app/services/prosody_service.py`（178 行目付近）と
  `app/services/pronunciation_service.py` — `_RATE_PENALTY_PER_WPS`。
- **状況:** **既知の不整合です。** ペナルティが非対称になっている歴史的な理由は、
  コードベースに記録されていません。本番データが得られた時点での v2 の
  キャリブレーションで扱うよう、フラグを立てています。
- **統一した場合のリスク:** 両方のサブスコアがずれる → overall_score の重みが変わる
  → サニティのベースラインを再生成する必要があります。

## v2 の定数（`app/services/v2/`）

セクション 1〜5 は v1 の定数です。v2 パイプラインには独自の定数があり、そのほとんどはデータから学習されます。

| 定数 | 値 | 場所 | 理由 |
| --- | --- | --- | --- |
| `SCORE_CURVE_EXPONENT` | `1.4` | `pronunciation_v2_service.py` | 専門家のスケールでの予測値（ほとんどが 6〜10）を、より厳しい v1 のスケールに写像します: `100 x (s/10)^1.4`。1.3 では `poor_001` が 59.4 となり、60 の線に近すぎました。合成クリップ 5 件で調整したものなので、実際の学習者の音声で再キャリブレーションしてください。発話の相関は 0.005 以下しか動きません |
| `MIN_HEARD_RATIO` | `0.2` | `pronunciation_v2_service.py` | 期待される音素のうち認識された割合が 20% 未満の場合、その音声は発話なしとして扱われます（ゼロスコア）。実際の speechocean762 の発話での最小値は 0.31 です |
| `mdd_threshold` | `1.48`（2 点満点中） | `scorer.json` | 音素スコアがこれを下回ると `is_correct_ipa = false` になります。fold 外の学習データ予測での誤発音 F1 が最大になるように選びました |
| `MIN_SAMPLES` | `400` | `phone_model.py` | HuBERT の畳み込みフロントエンドは、これより短い音声（25 ms）を受け付けません |
| `Z_CLIP` | `10` | `scorer.py` | まれな音素のワンホットは分散が非常に小さく、クリップしない z スコアは約 200 に達してフィッティングが破綻しました |
| 単語の誤発音しきい値 | `60` | `scoring_rules.py` | v1 と共通です（Azure も同じ値を使用） |
| ブレークのしきい値 | `0.8 s` / `0.15 s` | `scoring_rules.py` | v1 と共通です。v2 ではアライメントされた単語区間に適用します |

音素モデル、特徴量のレイアウト、音素インベントリのいずれかを変更する場合は、`scorer.json` の再学習が必要です（[training.md](training.md)）。品質は `scripts/speechocean762_eval.py --api v2` で確認します（[evaluation.md](evaluation.md)）。

## 定数を安全に更新する方法

1. 該当するサービスファイルで変更を行う。
2. ローカルサーバーを再起動する。
3. 次を実行する:
   ```
   python scripts/sanity_eval.py \
       --api-key=$API_KEY \
       --compare-baseline=tests/sanity_dataset/sanity_baseline.json
   ```
4. 終了コードが 0 の場合: 変更は許容範囲内です。下の変更履歴にエントリを追加して
   コミットします。
5. 意図的な再キャリブレーションで終了コードが 1 の場合: ベースラインを再生成し、
   両方のファイルをコミットし、ここに再キャリブレーションを記録します。
6. 意図しないリグレッションで終了コードが 1 の場合: 元に戻す。
