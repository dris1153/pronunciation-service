Pronunciation Validation Service

REST API that scores English pronunciation by comparing audio recordings against reference text. Returns IPA-level phoneme comparison, Goodness-of-Pronunciation (GOP), prosody, fluency, and an overall score compatible with Azure Speech sub-scores.

IPA Comparison

Per-phoneme alignment using Levenshtein DP with phonetic-similarity costs.

GOP Scoring

CTC log-posterior based, with remainder-aware frame distribution.

Prosody Analysis

Pitch via librosa pyin; intonation, range, contour, monotone detection.

Fluency Metrics

Speech rate + pause analysis from CTC forced-alignment word timing.

Tech stack

  • Web: FastAPI 0.115 + Uvicorn (single worker)
  • ASR model: facebook/wav2vec2-base-960h (CPU-only build)
  • IPA: g2p_en + ARPAbet → IPA mapping
  • Audio: librosa, soundfile, ffmpeg
  • Auth: X-API-Key + optional X-Service-Auth (per-user mode)
  • Deploy: Coolify self-host via Nixpacks (or Docker)
Audience This page is for developers integrating the service from their own backend. For end-user UX, scoring rationale, or the full API contract, see README.md and docs/scoring-constants.md in the source repo.

Architecture & Pipeline

One POST /api/v1/evaluate request triggers seven stages. All inference runs in a single worker; concurrency is bound by an asyncio.Semaphore (default 4 slots, queue overflow → 503).

Key invariants

  • Single worker only — service crashes at import-time if multi-worker is detected (1.2 GB model × N would OOM).
  • Pre-decode duration check — ffprobe (or soundfile.info for WAV/FLAC) rejects oversized audio BEFORE the full PCM expansion.
  • Concurrency cap — auto-detected via os.sched_getaffinity, capped at 4 slots.
  • 503 on queue overflow — clients should retry with backoff (see Errors section).

How Scoring Works

The previous section showed the engineering flow. This section explains the algorithm: how the final 0-100 score is derived from the ASR transcription.

Scoring runs four independent sub-scores from different signals, then combines them with an Azure-style weighted average that intentionally penalises the weakest dimension.

High-level scoring flow

Sub-score formulas (compact reference)

Sub-scoreFormulaSignal sourceRange
Accuracy 0.55·IPA + 0.45·GOP per-phoneme correctness + CTC log-prob 0–100
Completeness correct_words / total_ref_words × 100 word-level alignment + ≥60% accuracy threshold 0–100
Fluency 0.4·RateScore + 0.6·PauseScore speech rate + inter-word pause analysis 0–100
Prosody 0.55·Intonation + 0.20·Speed + 0.25·Rhythm pitch variance/range/contour + nPVI 0–100

Why the sort? Azure-style weighting

Sub-scores are sorted ascending then weighted asymmetrically: the lowest gets 40%, the other three split the remaining 60% (20% each). This intentionally penalises the weakest dimension most heavily — a user with great accuracy but monotone prosody can't hide behind the strong sub-scores. The formula matches Azure Speech SDK's PronScore behaviour.

Why sort, not average? A simple average treats all sub-scores equally and lets a strong one compensate for a weak one. The sorted formula reflects how a human listener perceives speech: the worst dimension dominates the impression.

Quality levels

Score rangeLevelFeedback
80 – 100ExcellentSpeech closely matches the reference
60 – 79GoodMinor improvements could be made
40 – 59FairSeveral sounds need practice
0 – 39PoorSignificant improvement needed
Detailed numeric example — "hello world" → "hallo world"

User reads "hello world"; ASR transcribes "hallo world" (1 vowel substitution: ɛ → æ in the first word).

Step 1 — Per-word IPA alignment

"hello":  ref [h, ɛ, l, oʊ]    actual [h, æ, l, oʊ]
          h=h ✓  ɛ→æ (different group, conf=0.0)  l=l ✓  oʊ=oʊ ✓
          → 3/4 correct = 75%

"world":  ref [w, ɝ, l, d]     actual [w, ɝ, l, d]
          all match
          → 4/4 correct = 100%

Overall IPA accuracy = 7/8 = 87.5%

Step 2 — GOP scoring (CTC log-prob normalised)

For each phoneme: average log-prob over its frames,
  clamp to [-25, -3], linear remap to [0, 100].

  Per-phoneme GOP scores (example):
    h=59.3  ɛ=68.5  l=72.0  oʊ=62.9
    w=63.9  ɝ=73.6  l=50.6  d=43.7

  Overall GOP = mean = 61.81

Step 3 — Compute the four sub-scores

Accuracy     = 0.55 × 87.5  + 0.45 × 61.81  = 48.13 + 27.81  = 75.94
Completeness = 2 / 2 × 100  (both words attempted ≥60%)        = 100.00
Fluency      = 0.4 × Rate(95.0) + 0.6 × Pause(91.0)            =  92.60
Prosody      = 0.55·Int(80) + 0.20·Spd(75) + 0.25·Rhythm(75)   =  77.75

Step 4 — Sort ascending and combine

Sub-scores: [Accuracy=75.94, Completeness=100, Fluency=92.60, Prosody=77.75]
Sorted:     [s₀=75.94, s₁=77.75, s₂=92.60, s₃=100.00]

Overall = 0.4 × 75.94 + 0.2 × 77.75 + 0.2 × 92.60 + 0.2 × 100.00
        = 30.376    + 15.550     + 18.520     + 20.000
        = 84.45

Level: EXCELLENT (≥ 80)  ✓

Note: s₀ = Accuracy = 75.94 got the 40% weight — even though Accuracy is the lowest sub-score, the user's overall impression remains EXCELLENT because all other dimensions are strong. A user with the same Accuracy but Prosody = 35 would land at FAIR instead, since Prosody = 35 would become s₀.

Source of truth Numeric example values mirror README.md's scoring example. For implementation details see app/services/pronunciation_service.py; for constants rationale see docs/scoring-constants.md.

Authentication & Internal Microservice Mode

Standard auth — X-API-Key

Every protected endpoint requires X-API-Key. Generate a strong key:

python -c "import secrets; print(secrets.token_urlsafe(32))"
BehaviourCondition
Auth disabledAPI_KEY env var is empty (dev only — server logs warning at startup)
401Header missing when API_KEY is set
403Header present but value mismatch
200Header matches
Production guard With DEBUG=false, startup fails immediately if API_KEY is empty, < 32 chars, or matches a known weak placeholder (e.g. change-me, test).

Internal Microservice Mode (per-user rate limit)

By default the service rate-limits per source IP. When you call it from your own backend, all your users share that one IP — 1000 users would burn a single quota.

Per-user keying lets the service rate-limit on the real end-user you forward in a header. Each user gets their own quota; one spammy user doesn't affect the others.

Headers contract

HeaderRequired whenPurpose
X-API-KeyAlwaysService-level auth (existing)
X-Service-AuthYou want per-user keying Must match SERVICE_API_KEY env
X-End-User-IdYou sent X-Service-Auth The end-user this request is for

Decision table — what becomes the rate-limit key

Direct TCP peerService auth match Valid X-End-User-IdResulting key
Untrusted CIDR(any)(any)ip:<peer>
Trusted CIDRNo(any)ip:<peer>
Trusted CIDRYesNoip:<peer>
Trusted CIDRYesYesuser:<id> ✓
Spoof-safe by design Trust gate uses the direct TCP peer, not the XFF-resolved address. An attacker on 1.2.3.4 cannot forge X-Forwarded-For: 172.17.0.5 to bypass the check.

Anonymous users

For users who haven't logged in (trial / demo widget):

X-End-User-Id: anon-<session-uuid>

Generate the UUID client-side, store in localStorage, one per browser tab.

TypeScript wrapper (with retry-backoff)

const SERVICE_URL   = process.env.PRONUNCIATION_URL!;
const API_KEY       = process.env.PRONUNCIATION_API_KEY!;
const SERVICE_AUTH  = process.env.PRONUNCIATION_SERVICE_AUTH!;

export async function evaluatePronunciation(
  audio: Blob, referenceText: string, userId: string
) {
  const headers = {
    "X-API-Key":      API_KEY,
    "X-Service-Auth": SERVICE_AUTH,
    "X-End-User-Id":  userId,
  };
  const body = new FormData();
  body.append("audio", audio, "audio.wav");
  body.append("reference_text", referenceText);

  for (let attempt = 0; attempt < 3; attempt++) {
    const r = await fetch(`${SERVICE_URL}/api/v1/evaluate`,
                          { method: "POST", headers, body });
    if (r.status === 503) {                 // queue full — retry
      const ra = Number(r.headers.get("retry-after") ?? "1");
      await new Promise(res => setTimeout(res,
        Math.min(2 ** attempt * 1000, ra * 1000)));
      continue;
    }
    if (r.status === 429) throw new Error("End-user quota exceeded");
    if (!r.ok) throw new Error(`Service ${r.status}: ${await r.text()}`);
    return r.json();
  }
  throw new Error("Service unavailable after 3 retries");
}

Python wrapper

import asyncio, os, httpx

URL          = os.environ["PRONUNCIATION_URL"]
API_KEY      = os.environ["PRONUNCIATION_API_KEY"]
SERVICE_AUTH = os.environ["PRONUNCIATION_SERVICE_AUTH"]

async def evaluate(audio: bytes, reference_text: str, user_id: str) -> dict:
    headers = {
        "X-API-Key":      API_KEY,
        "X-Service-Auth": SERVICE_AUTH,
        "X-End-User-Id":  user_id,
    }
    files = {"audio": ("audio.wav", audio, "audio/wav")}
    data  = {"reference_text": reference_text}
    async with httpx.AsyncClient(timeout=120.0) as client:
        for attempt in range(3):
            r = await client.post(f"{URL}/api/v1/evaluate",
                                  headers=headers, files=files, data=data)
            if r.status_code == 503:
                ra = int(r.headers.get("retry-after", "1"))
                await asyncio.sleep(min(2 ** attempt, ra))
                continue
            if r.status_code == 429:
                raise RuntimeError("End-user quota exceeded")
            r.raise_for_status()
            return r.json()
    raise RuntimeError("Service unavailable after 3 retries")

Error Handling & Retry

Every error response has the same envelope:

{ "detail": "<human-readable message>",
  "error_code": "<machine code>" }

Status matrix

CodeMeaningRecommended client action
200OKUse response body
400Bad audio (empty / oversized / wrong format / decode failed)Surface to user; suggest re-record
401 / 403API key issuePage on-call; config bug, not user error
422reference_text rejectedSurface to user (length / invalid chars)
429Rate limit exceeded for this keySurface; throttle UI; do not auto-retry
500Internal errorRetry once; if persists, generic error
503Inference queue fullRetry with exponential backoff (1 s, 2 s, 4 s, max 3)
504Request timeout (> 90 s)Retry with smaller audio chunk
Don't auto-retry 429 429 means the user (or the BE keyed by IP) has burned their quota. Auto-retrying just confirms the cap and burns more time. Surface the error and let the user wait it out, or upgrade their tier.

Retry-backoff pattern

503 carries Retry-After in seconds. Use it as an upper bound, but apply exponential backoff for the lower bound:

delay_seconds = min(2 ** attempt, int(retry_after_header))
# attempt: 0 → 1 s, 1 → 2 s, 2 → 4 s; max 3 attempts

Real wrappers shown in the Authentication & Internal Mode section.

Common pitfalls

  • "Could not determine audio duration" — usually ffmpeg/ffprobe missing on the server. Install the system package or rely on imageio-ffmpeg.
  • Permanent 429 in production — you're keying by IP. Enable Internal Microservice Mode and forward X-End-User-Id.
  • 504 on perfectly normal audio — likely CPU-starved container or model not warmed up. Send 1 dummy request after deploy.

Operational logs

Production logs are JSON one-line-per-record (loguru serialize=True). Each request emits one request_completed entry:

{ "request_id": "<uuid>",
  "endpoint":   "/api/v1/evaluate",
